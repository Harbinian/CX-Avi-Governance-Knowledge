# 会话规则的使用场景

以下是方法示例，供使用者检查AI是否正确执行，不代表已经进行真实业务验收。所有业务情景均为虚构，不是正式制度。

| 用户输入或情境 | AI应如何处理 |
|---|---|
| “我要整理实际做法”，但载体或保存期限未知 | 记录事实缺口及来源，不按相近制度猜成现状规则；继续其他有据内容 |
| “我要设计新流程”，提出新审批或载体方案 | 标明建议、已确认设计及约束，不声称已有实际做法或其他部门同意 |
| “第一次编制，材料都在这里” | 实际读取材料，调用grill-me辅助明确行为、条件与角色；充分材料直接复用，选择关键情景核对理解 |
| “这是最新JSON，继续补表单字段” | 恢复该稿与已确认内容，保留稳定标识；完成有据可确定的字段整理，不从头访谈、不声称用户已认为本版符合事实 |
| “这版行为、条件和角色都符合实际” | 记录对应版本和表示，调用grill-me逐个情景提问，核对用户答案 |
| “符合事实”后，答案与草稿不同 | 定位差异并查证，不直接判用户错；证据支持答案时修改草稿，支持草稿时指出答复问题，缺证时保留待核对 |
| “我认可这个新方案” | 固定方案与范围，用grill-me做设计情景推演；结果记为设计一致性与约束核验，授权及待验证假设另列 |
| 用户只回答“领导审批”，没有材料 | 追问本场景具体审批角色、动作及授权依据；提供查证建议，不默认最高职务者就是审批人 |
| 核验后改变退回条件或执行角色 | 同步修改正文与JSON，标明旧核验覆盖范围失效；取得新版符合事实的明确表示后核验受影响场景 |
| JSON技术校验全绿，但保存期限仍未知 | 报告技术通过及业务缺口，不宣称完整、已批准或已发布 |
| 四项成果已齐，但业务量、时间或容量缺失 | 工作平衡报告列出已知贡献、待评和待补，不填0、默认3分或160小时，不声称量化评价完成 |
| 当前工具没有原生技能调用能力 | 读入同包技能并说明按文件执行；无法读文件则索取必要内容，不假称调用成功 |
