# 流程编制会话规则

依据：用户于2026-10-08规定首次／续编的grill-me使用方式，于2026-10-09要求完整编制技能，并确认区分现状梳理与新设计，以及设计认可后的情景推演。本文件落实AI作业方法，不新增公司业务职责、审批权或已生效制度。

## 先明确业务目标

启动时分别记录会话起点“首次／继续”与业务目标“梳理实际流程／设计新流程”；旧稿已明确目标时复用。现状梳理依据材料和实际说明，缺证保留缺口；新设计可提出方案，但分别标注建议、已确认设计、既有事实和待验证假设。设计认可不能升级为已经运行、其他部门同意或公司批准。

## 识别本次起点

| 起点 | 处理 |
|---|---|
| 首次编制一个流程，包括已提供充分材料 | 必须调用同包 grill-me，辅助明确行为、条件和角色；充分材料直接复用，通过关键场景确认理解 |
| 已有流程草稿继续编制或修订 | 先读取用户指定的最新草稿和续接记录，保留已确认内容，不从头重问 |
| 续编中用户明确认为当前草稿符合事实 | 必须调用 grill-me，逐个情景提问，核对答案与依据，记录发现并修正草稿 |
| 新设计任务中用户明确认可当前方案 | 调用grill-me做设计情景推演，记录设计一致性与约束核验；实际事实另按事实依据核验 |
| 续编中用户仅说“继续”或只提供修改要求 | 完成已明确修订，澄清必要缺口；不声称已获得符合事实的表示，也不启动整套事实核验 |
| 仅修复JSON结构错误 | 修复可据规则确定的问题；涉及行为、条件或角色时取得依据，并同步受影响正文 |

原生技能调用能力因工具而异。支持技能的环境调用 `.agents/skills/grill-me/SKILL.md`；其他能读取文件的AI按文件方法执行，并说明实际方式。不能读取文件时由使用者提供同版本必要内容。不得虚构调用成功。

## 首次编制：先澄清，再形成草稿

沿依赖关系推进，一次只问一个关键问题；先读取材料和已有确认。默认先解决单流程边界，再解决主线行为、判断条件和角色，随后补交接、异常、数据与表单。该顺序用于避免后续依赖悬空，不强制用户逐阶段重复批准。

每个问题说明正在明确什么及为什么需要，并给出推荐答法或有依据的设计建议。现状问题没有证据时不预设答案；建议方案要保留建议属性，不能通过选项暗示它已经是实际做法。

| 需要明确 | 提问应得到的内容 |
|---|---|
| 行为 | 谁对什么对象做什么、依据什么、产生什么结果，如何判断办理完成 |
| 条件 | 触发与前提、判断标准、不同结果的去向、退回后从哪里恢复、实际存在的退出或例外 |
| 角色 | 执行、协作、审核、批准等具体责任，各自动作、适用范围、授权依据及交接边界 |
| 数据与表单 | 当前记录与字段，何时创建、读取或修改，修改哪些字段，值从哪里取得 |

部门职能和岗位配置用于辅助定位，不自动产生上述任务角色。岗位相同不表示动作相同；角色名称相同也不表示具有同一审批权。执行主体、控制节点与3000治理账号权限分别表达。

同一问题回答后，简短记录答案、来源和影响，继续能够推进的工作。缺口只暂停依赖部分；用户不知道时改用查证路径，不反复逼用户猜同一个答案。已有授权允许提出方案，但不能把建议标为现状事实或已批准安排。

## 继续编制：在用户认为符合事实后核验答案

先固定本轮文件名、版本及可取得的实际文件SHA-256；无法计算时明确未计算，不编造摘要。用户关于“符合事实”的表示必须对应这一版草稿，保留其原话或准确摘要及记录时间。AI整理出的内容摘要本身不代表用户已作此表示。

用户作出明确表示后，调用 grill-me，按当前流程实际结构提出情景问题。每次只问一个，不提前显示预设业务答案。推荐内容说明如何完整作答或如何查证。

该表示可以针对整个流程，也可以针对本轮已编制的一部分；记录表示范围，并核验对应内容及受影响的前后步骤，不要求全稿完成才开始提问。局部核验结果不能推广为全流程符合事实。

可用的问题形式：

- 正常办理：“材料达到什么条件后，由谁做哪项处理，凭什么结果交给下一步？”
- 退回补正：“这一项不符合要求时，谁说明原因、退给谁，补齐后从哪个环节恢复？”
- 角色权限：“遇到这个例外，谁有权作决定，执行人依据什么办理？”
- 数据变化：“这一步改变了哪几个字段，原值和新值分别来自哪里？”
- 并行交接：“如果一方尚未完成而另一方已完成，什么时候可以继续，由什么结果证明？”

按实际关键路径覆盖行为、条件和角色；新增或修改部分及其上下游优先。不存在的代理、例外、并行或业务阈值不为凑问题而加入流程。已在当前固定版本有据核验的内容可以复用记录。

## 怎样判断答案是否正确

核对依据来自用户指定原始材料、明确业务说明及有权主体的确认。草稿用于检验表达一致性，不能单独证明业务正确；AI建议答案也不是评分依据。

| 判定 | 使用条件与处理 |
|---|---|
| 有据支持 | 答案与可定位依据、当前草稿及适用条件相符，记录支持位置；只说明本问题核验结果 |
| 与草稿一致，业务依据待补 | 答案与草稿一致，但现状或授权缺少可定位依据，保留待核对，不判业务正确 |
| 存在不一致 | 列出答案、草稿与材料之间的具体差异；先查明是草稿错误、答复错误、材料不适用还是现状与制度不一致 |
| 依据不足 | 无法判断，记录缺口和可执行的查证方式；不强制用户选一个答案 |

有明确依据证明回答错误时，指出错误内容、正确口径及来源，并说明受影响步骤；依据证明草稿错误时，修正草稿。只有有权人员能决定的新安排，保留建议或待确认状态。不得因为回答较新就覆盖旧确认，也不得因为与草稿不同就认定用户答错。

记录采用 [任务与问答记录模板](../templates/process-task-record.md)：问题编号、场景、用户答复、依据、判定、影响和处理结果。未解决的实质缺口采用 [待确认事项模板](../templates/process-pending-items.md)。用户表示符合事实与问答判定都留在JSON之外，不增加3000不支持的字段。

## 新设计：认可方案后做情景推演

新设计任务中，固定用户认可的方案文件、版本及范围后，调用grill-me做情景推演。每次提出一个场景，让用户先说明动作、条件、结果和下一步，再核对方案一致性、已知制度与权限约束、可用资源及待验证假设。覆盖方案涉及的正常办理、退回、例外和角色边界，实际存在的并行与会签也要核对。

设计推演判定为“设计一致且符合已知约束”“设计存在不一致”“约束／授权依据不足”或“假设待验证”。未运行时不判现状事实已验证，缺少授权时不判已获批准。新设计中的既有事实仍按上一节核验；对方案的认可与对事实的表示分别记录。

## 修订与本轮完成

核验发现问题后，同步修改受影响的正文、JSON和工作平衡报告，保留既有技术标识及其余事实。修改了关键行为、条件或角色，事实核验须重新取得用户对新版符合事实的表示，设计推演须重新取得对新方案的认可，再提问受影响场景；不能将旧版核验结果套到新版。

本轮记录说明哪些场景有据支持、哪些尚有差异，以及技术检查是否实际通过。有未解决问题时可以交付明确标注的阶段草稿，不声称全流程已符合事实。用户的事实表示、AI答案核验、3001技术检查、3000部门核对与正式审核分别记录，互不替代。
