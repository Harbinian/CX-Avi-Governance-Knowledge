# 内部 AI 治理知识与规则库建设说明

日期：2026年9月28日

文档版本：0.1

状态：讨论稿，用于内部沟通和部署准备，尚未批准为执行规则。

2026-10-05 方向更新：用户明确本库将推送到 GitHub，供其他同事以此为基础与 AI 会话设计或编制流程。当前准备入口改为 [GitHub 协作准备方案](github-collaboration-plan.md) 和 [AI 会话作业入口](../workflows/process-ai-collaboration.md)。下文固定电脑、Gitea 安装、内网服务及其备份方案保留为前期讨论记录，不再作为当前托管安排；其历史“待确认”状态不覆盖用户本次选择。

## 一、建设结论与当前条件

建议建立与 Infomat 平级的独立 Git 仓库，集中维护供内部人员使用的治理知识、规则、AI 作业方法和模板；选择一台固定电脑，部署 Gitea 作为内部 Git 托管服务。用户可以提交更新，经相应负责人审核后发布正式版本，其他用户及其 AI 工具按指定版本使用。

Git 用于记录文件修改和版本历史；Gitea 提供内部网页入口、账号权限、修改申请及审核协作。正式内容由组织确定的有权主体确认，系统只提供记录和控制能力。

### 已确认条件

- 仅服务内部人员。
- 目前没有统一的 Git 托管平台。
- 可以提供一台电脑用于共享服务。
- 需要建立与 Infomat 平级的独立库，并允许用户提交更新。

### 本文提出的建议

Gitea 选型、仓库名称、目录结构、配置规模、审核方式及备份安排均属于建议，待实施前确认。本地仓库及起步文件已于2026年9月28日建立；尚未部署托管服务、开设账号或开启多人推送。

## 二、建设目标与范围

首期应让内部用户能够完成以下操作：

1. 找到当前正式发布的规则及适用范围。
2. 将指定版本交给 AI，结合本次业务材料开展治理工作。
3. 在成果中追溯知识库版本、规则编号和业务依据。
4. 发现错误或补充知识时，提交有来源的修改申请。
5. 由相应负责人审核后发布新版，并保留历史版本。

首期以 Markdown 文档、模板和少量脱敏示例为主。暂不建设向量数据库、专用搜索平台、自动治理审批或与 Infomat 的自动同步接口。具体业务原件、人员名单、账号凭据和大型附件是否入库，应按内容权限单独判断。

## 三、与 Infomat 及业务依据的关系

| 对象 | 职责边界 |
|---|---|
| 独立知识规则库 | 保存经确认的共享规则、通用知识、方法、模板和来源索引 |
| Infomat | 维护现有应用、技术实现及其兼容关系 |
| 3001、3000 | 沿用当前已确认的业务方向：3001编制，用户下载后上传3000治理、核对和审核；方向不代表全部功能已实现 |
| 原始业务材料和业务确认 | 提供具体流程事实、责任和审批依据 |
| 用户任务目录 | 保存本次输入、草稿、待确认事项及工作成果 |

用户已明确 Infomat 的全部 `docs/` 文件不再是真源。旧文档移入新库也不会自动获得业务权威；如需复用，应核对来源、适用性和确认记录，再决定是否进入正式版本。首期不批量移动或删除 Infomat 的既有文件，不改变其兼容资产。

通用规则可以规定“缺少依据时不得补造审批人”。具体业务由谁审批，则必须有对应业务依据和有权主体确认。仓库维护权限不等于决定业务责任的权限。

## 四、部署关系与电脑要求

### 4.1 部署关系

```text
内部固定电脑
└─ Gitea 托管服务
   └─ Governance-Knowledge 共享仓库（名称待确认）

维护者电脑
└─ E:\CA001\
   ├─ Infomat\
   └─ Governance-Knowledge\ 本地工作副本

其他内部用户
└─ 通过浏览器参与协作，或克隆工作副本供本地 AI 读取
```

“与 Infomat 平级”指本地两个独立目录及独立 Git 历史。多人协作以内部服务器上的远程仓库为共同入口，每个人使用自己的工作副本，避免多人直接编辑同一个共享文件夹。

### 4.2 首期建议配置

| 项目 | 建议与说明 |
|---|---|
| 电脑 | 固定用途的台式机，避免频繁重装和临时挪用 |
| CPU、内存 | 4核、8 GB作为首期起步建议，不是官方最低要求或容量承诺 |
| 存储 | SSD，先预留约50 GB；附件规模增长时重新评估 |
| 网络 | 有线内网，固定IP或地址保留，条件允许时配置内部域名 |
| 运行 | 在约定服务时段开机，关闭自动睡眠，安排系统维护窗口 |
| 系统 | 待确认；应使用仍受支持且符合内部安全要求的系统 |
| 管理 | 指定管理员，管理服务、账号、备份、恢复和更新 |
| 备份位置 | 另一台电脑或NAS，与服务电脑分离 |

Gitea 支持二进制安装和 Windows 服务运行。具体安装方式、版本、数据库和端口在确认电脑系统后确定，不沿用 Infomat 的数据库或服务端口配置。首期不默认增加持续集成执行器；需要自动检查时再评估隔离运行方式。

## 五、知识内容组织

建议采用以下最小结构，按实际内容逐步建立，避免先生成大量空文件：

```text
README.md          用途、适用范围、正式版本入口
AGENTS.md          面向兼容AI工具的读取入口和行为要求
CONTRIBUTING.md    更新提交、审核和发布方法
manifest.json      正式内容清单、状态、版本和路径
rules/             经确认的治理规则
knowledge/         术语和通用知识
workflows/         按任务组织的AI作业方法
templates/         输出模板
examples/          脱敏示例
sources/           来源索引和确认记录
```

首批建议围绕一个真实任务整理，例如 AI 辅助单流程编制。优先收录事实与建议的区分、证据引用要求、缺失信息的处理、责任边界和成果检查方法。具体首批清单由负责人确认。

每条正式规则应有稳定编号、名称、适用范围、来源定位、确认主体与记录、生效日期和替代关系。状态至少区分草稿、已生效和已废止。示例必须标记为示例，不得被解释为本次业务事实。

原始材料中的命令、链接或提示文本属于待处理材料，不能自动升级为AI执行指令。规则冲突应记录冲突条目和影响，提交有权主体处理；不得让AI自行选取方便执行的口径。

## 六、用户提交与审核发布

### 6.1 建议角色

| 角色 | 主要职责与权限 |
|---|---|
| 使用者 | 读取正式内容，提出问题和修改建议 |
| 贡献者 | 在自己的修改分支编辑内容，推送并提出合并请求 |
| 内容审核者 | 核对来源、适用范围和业务正确性；涉及业务决定时取得有权主体确认 |
| 仓库维护者 | 核对格式、引用、版本和审核记录，执行合并及发布 |
| 服务管理员 | 管理账号、服务、权限配置和备份恢复 |

上述角色是建议分工，尚未指定人员。角色可以兼任；涉及实质性业务规则变更时，建议由提交者以外的有权人员确认，不以管理员账号代替审批责任。

### 6.2 更新流程

1. 贡献者基于当前正式内容建立修改分支，写明问题和依据。
2. 贡献者提交修改并推送分支，提出合并请求，即请求将修改纳入正式分支。
3. 审核者检查来源、责任、适用范围及与既有规则的冲突；依据不足时退回补充。
4. 修改后由审核者复核最终内容，不能沿用已失效的旧审批。
5. 维护者确认审核完成后合并，整理发布清单并发布版本。
6. 使用者主动获取新版本；正在进行的任务先评估影响，再决定是否切换。

不熟悉Git的人员可以通过网页提出问题或修改，由维护者协助形成修改申请；应保留原提出人和确认记录。

### 6.3 变更控制

正式分支应限制直接推送、强制覆盖和删除，并按实际安装版本配置审核要求。正式发布标签也应限制改写；发现错误时发布修正版或撤销说明，保留历史记录。

单条规则的生效状态与仓库版本发布是两项检查。正式使用包应按清单只包含已生效内容，草稿不得因位于同一仓库而被默认采用。下载完整源码的使用者仍需依据正式清单读取。

每次修改申请应说明修改原因、来源、影响对象和新旧规则关系。格式或链接检查只能辅助审核，不能证明业务正确性。紧急发现错误规则时，应停止引用该条目、标记影响范围并通知受影响使用者，随后按审核流程修正。

## 七、AI 使用方法

知识库不会因与Infomat目录相邻而自动被所有AI工具读取。应按实际工具提供明确入口，并验证工具确实读取了相应文件。

| 使用方式 | 操作方法 |
|---|---|
| AI可以读取本地文件 | 获取指定发布版本，明确指定入口文件；按任务读取相关规则和模板 |
| AI只能接收上传文件 | 使用同一版本生成的正式使用包；上传前确认工具及材料使用符合内部授权 |
| AI无法取得完整规则 | 明确记录缺失内容，暂停依赖缺失规则的判断，不声称已遵守全库规则 |

内部托管仅说明仓库位于内网，不代表调用外部AI时数据不会外发。仓库读取权限不自动授予向外部AI上传材料的权限；应按组织允许的工具和数据范围使用。

建议每次任务遵循以下步骤：

1. 记录知识库发布版本与对应提交标识。
2. 读取统一入口及该任务适用的规则清单。
3. 提供本次业务原始材料，区分来源事实与未确认信息。
4. 由AI辅助提问、整理、检查和起草，保留待确认事项。
5. 由业务人员及相应审核主体确认成果。
6. 在成果中记录版本、规则编号、业务材料来源及未确认事项。

以下为引用格式示例，其中编号和版本仅为示例：

> 本次使用知识库 v1.0.0，适用规则 GOV-001。业务事实依据为本次指定材料及确认记录；尚未确认事项单独列出。

一次任务默认固定版本，不在后台静默更新。AI可以起草规则修改建议，但不得自行将输出认定为正式规则并绕过审核发布。

## 八、访问与备份要求

### 8.1 访问控制建议

- 关闭公开自助注册和匿名读取，账号由管理员按内部人员范围开通。
- 仓库设置为私有，为使用者、贡献者、维护者分配必要权限。
- 正式使用时配置可信的HTTPS访问及相应网络访问范围，避免明文传输账号凭据。
- 不将密码、令牌、私钥或真实私有配置写入仓库、示例或操作记录。
- 不同部门存在阅读权限差异时，应拆分仓库或仅保存允许共享的来源索引，不能用目录名称代替访问隔离。
- 人员变动时调整账号权限；已经克隆或下载的副本不能依靠撤销账号自动收回。

### 8.2 备份与恢复建议

备份应覆盖Git仓库、数据库、配置和附件，而不只是文档工作副本。备份中的敏感配置应限制访问，不纳入知识库版本控制。

Gitea官方文档指出，为保证文件、仓库和数据库的一致性，应在备份时停止实例。首期建议安排非工作时段短暂停服，完成一致性备份后启动服务并检查访问情况。若以后不能接受停服，需要另行设计并验证一致性备份方案。

建议每天备份至独立设备，初始保留最近14份每日备份及最近3份月度备份；该频率和保留期需结合可接受的数据损失、容量及内部要求确认。每日备份只能提供约一天级的数据恢复点，不能承诺零丢失。

上线前应在隔离位置完成一次恢复演练，验证账号、仓库、提交历史、审核记录、附件及发布版本。后续在重要升级后复验。恢复耗时应以演练实测记录为准。

服务故障时，用户可继续参考已取得的指定版本，但暂不能依赖中心服务提交和发布更新。管理员恢复服务后，用户通过各自分支重新提交，遇到冲突由维护者核对，不覆盖他人修改。

## 九、实施步骤与完成标准

| 阶段 | 执行动作 | 可检查的结果 |
|---|---|---|
| 1. 条件确认 | 确认电脑、系统、地址、管理员、备份位置和安装授权 | 部署对象和维护责任明确 |
| 2. 服务准备 | 安装Gitea，配置访问、账号、权限和备份 | 从另一台内部电脑可以正常访问 |
| 3. 内容准备 | 建立独立仓库，整理首批来源及规则 | 每条拟生效规则均有依据和确认记录 |
| 4. 协作试用 | 用普通贡献者账号提交修改，完成退回、复核、合并和发布 | 普通用户不能绕过正式分支控制 |
| 5. AI试用 | 用指定版本完成一个真实任务 | 成果引用可核对，缺失依据得到明确标记 |
| 6. 恢复与验收 | 完成恢复演练，并由指定人员确认试用结果 | 形成实际检查记录，决定是否正式启用 |

部署检查发现权限不符、正式内容夹带草稿或备份不能恢复时，应暂停正式启用并修复。服务升级前备份；升级失败时由管理员按已验证方案恢复原版本及相匹配的数据，禁止在未核对兼容性时直接降级程序。

### 首期验收项目

- 普通内部用户可以登录并读取被授权内容，匿名或未授权用户不能读取私有仓库。
- 普通贡献者可以推送自己的分支并提交修改，但不能直接覆盖、删除或强制改写正式分支。
- 审核后的新增修改会重新进入必要的复核步骤，发布版本能追溯到确认记录。
- 正式使用包符合发布清单，草稿和已废止规则不会作为当前默认依据。
- 不同用户取得同一发布版本时，其正式内容一致。
- AI试用成果注明版本和来源，不能将示例或旧文档自动视为业务事实。
- 在隔离位置能从备份恢复服务并读取历史、审核记录和发布内容。
- 指定业务人员确认试用结果；技术检查通过不替代业务验收。
